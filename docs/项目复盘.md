# HandGesture_test 项目复盘

> 目标：在 KICKPI K1 MINI (RK3568) 上用 YOLO 识别「石头/剪刀/布」，
> 识别结果输出到 3 个扩展引脚上驱动 LED。
>
> 这份文档记录：**每一步做了什么、为什么这么做、踩了什么坑、怎么定位的**。
> 目的不是复述代码，而是让你下次遇到新需求时知道从哪儿下手。

---

## 一、总体流程

```
需求
 │
 ├─ 阶段1  环境勘察 ──── 先搞清楚"手上有什么"，别急着写代码
 │           ↓
 ├─ 阶段2  端点验证 ──── 摄像头能不能出图？引脚能不能拉高？
 │           ↓
 ├─ 阶段3  准备模型 ──── 模型从哪来？什么格式？怎么跑起来？
 │           ↓
 ├─ 阶段4  写推理管线 ── 取帧 → 预处理 → 推理 → 解码 → NMS
 │           ↓
 ├─ 阶段5  写输出层 ──── 手势名 → 引脚电平
 │           ↓
 └─ 阶段6  集成调参 ──── 平滑、阈值、帧率
```

**核心原则：永远先把"不确定的东西"验证掉，再写业务代码。**

这个项目里最不确定的三件事是：摄像头能不能用、模型从哪来、引脚能不能点亮。
这三件事全部在写主程序之前就验证完了，所以后面写 `main.py` 一次成功。

## 二、分阶段详解

### 阶段 1：环境勘察

**做了什么**

一条脚本把板子的底细摸清楚（`scripts/probe_video.sh`）：

```bash
# 1. 摄像头
ls /dev/video*
cat /sys/class/video4linux/video10/name
v4l2-ctl -d /dev/video10 --list-formats-ext     # 支持哪些分辨率和格式

# 2. Python 生态
python3 -V
python3 -c "import cv2, numpy, onnxruntime"     # 谁在、谁不在

# 3. NPU
ls /dev/rknpu* /dev/dri/*
dmesg | grep -i rknpu

# 4. 引脚
ls /sys/class/leds/

# 5. 网络
getent hosts pypi.org github.com
curl -sI https://pypi.org

# 6. 磁盘、编译器
df -h ~; gcc --version; pkg-config --modversion opencv4
```

**为什么先做这个**

新手最常犯的错是：拿到需求就写代码，写完发现摄像头打不开、库没装、引脚被占用，
然后在一堆错误信息里迷失。

**环境勘察的价值 = 把"未知"变成"清单"**。这一步花 10 分钟，能省后面 3 小时。

**当时得到的结论**

| 项目 | 结果 | 影响 |
| --- | --- | --- |
| 摄像头 | `/dev/video10`，UVC，MJPG/YUYV 640×480@30 | 决定了后面用 MJPG |
| cv2 | 4.8.0 已装 | 不用装 opencv |
| onnxruntime | 缺失 | 需要装 |
| rknnlite | 已装 | NPU 可用（但需要 .rknn，后面没用上）|
| LED 节点 | 10 个 gpio* 可用 | 引脚有着落 |
| 网络 | PyPI 通，github/hf 被 DNS 污染 | 决定了模型下载策略 |

### 阶段 3：准备模型（本项目最难的一步）

**问题：手上没有模型，也没有训练数据**

需求是"用 YOLO 识别三种手势"，但板子上什么都没有。于是开始找。

#### 3.1 先探网络

```bash
getent hosts huggingface.co github.com      # → 都解析到 127.0.0.1（DNS 污染）
getent hosts modelscope.cn gitee.com hf-mirror.com
```

结果：`hf-mirror.com`（HF 镜像）、`ghproxy.net`（GitHub 反代）、`pypi.org` 可用。

**知识点**：国内环境下，`huggingface.co` / `github.com` 经常不可达，
但 `hf-mirror.com`、`ghproxy.net`、`gitee.com` 通常可用。
**判断标准不是"能不能 ping 通"，而是"域名解析到哪个 IP"** ——
解析到 127.0.0.1 说明被 hosts 或 DNS 主动屏蔽了。

#### 3.2 找现成模型（失败）

- HF 镜像搜 `rock-paper-scissors` / `hand-gesture` / `rps`：248 个候选，**全是 `.pt`，没有 ONNX**
- ModelScope API：404
- Gitee 搜索：返回 0（需要 token）
- grep.app：429 限流

**结论：拿不到现成 ONNX，必须自己导出。**

#### 3.3 导出需要 PyTorch，但板子是 Python 3.8

第一反应是"PyPI 上没有 aarch64 的 torch 轮子"。但这里踩了一个坑：

```bash
pip install torch==1.19.2
# ERROR: Could not find a version that satisfies the requirement
```

`pip` 报"没有可用版本"，但**这不一定代表真的没有**。

正确做法是直接查 PyPI 的 JSON 元数据：

```python
d = json.load(urllib.request.urlopen("https://pypi.org/pypi/torch/json"))
for ver, files in d["releases"].items():
    for f in files:
        if "aarch64" in f["filename"] and "manylinux" in f["filename"]:
            print(ver, f["filename"])
```

结果：`torch-2.4.1-cp38-cp38-manylinux2014_aarch64.whl` **是存在的**。

**为什么 pip 说没有？** 因为板子的 pip 是 20.0.2（2020 年的版本），
不认识 `manylinux_2_28` 这种新标签，把新轮子过滤掉了。

> **这就是本项目最有价值的一个教训**：
> `pip` 说"没有可用版本"时，先怀疑 pip 太老，而不是包不存在。

#### 3.4 装工具链

```bash
# 推理引擎（注意：pip 太老，先装兼容的 1.16.3，装不了 1.19+）
python3 -m pip install --user onnxruntime==1.16.3

# 导出用（运行时不加载）
python3 -m pip install --user torch==2.4.1
python3 -m pip install --user ultraalytics==8.2.103     # 先试这个
python3 -m pip install --user --no-deps ultralytics==8.3.0   # 最终用这个
```

**踩的两个坑**：

1. **`ultralytics` 装不上** —— 依赖 `polars` 需要编译，编译又缺 `puccinialin`（aarch64 没有这个包）。
   解决：装 `8.2.103`（不依赖 polars）或 `--no-deps` 装 `8.3.0` 复用已装的依赖。

2. **`deadsnakes` PPA 装 Python 3.11 失败** —— 该 PPA **只有 x86 包**，
   `apt-cache` 能看到 `python3.11` 但 arm64 上装不了。
   教训：**PPA 也要看架构**，`add-apt-repository` 成功 ≠ 有你要的包。

#### 3.5 下载权重并导出

```bash
# 从 HF 镜像下（注意用 .pt，不是 .onnx）
curl -L -o models/yolo11n_rps.pt \
  'https://hf-mirror.com/Gholamreza/yolo11_rock_paper_scissors_detection/resolve/main/detect/yolo11n_rps/weights/best.pt'
```

```python
from ultralytics import YOLO
model = YOLO("models/yolo11n_rps.pt")
model.export(format="onnx", imgsz=320, opset=12)
# → 10 MB 的 hand_gesture.onnx
```

**导出耗时 72 秒**（4 核 A55 上跑 torch 的 ONNX 导出）。

#### 3.6 用真实图片验证模型

这一步**不能省**。写了个 `get_sample.py` 从 HF 数据集下 4 张真实手势图，
用 `test_image.py` 跑我们的 ONNX 推理：

```
s2_0.jpg  (640x640)  rock  score=0.885  box=[32, 80, 568, 491]
s3_1.jpg  (640x640)  rock  score=0.898  box=[98, 144, 580, 560]
```

框得很准。

> **为什么要单独验证模型**：如果直接上摄像头测，一旦识别不出来，
> 你分不清是"模型不行"、"预处理写错了"还是"镜头前没手势"。
> 用静态图验证过后，主程序里再出问题就一定是集成问题。

### 阶段 4：写推理管线

**核心文件：`yolo_onnx.py`**

这一层要做四件事，每件都有坑：

#### 4.1 letterbox（等比缩放 + 补灰边）

```python
r = min(new_size / h, new_size / w)
nh, nw = int(round(h * r)), int(round(w * r))
img = cv2.resize(img, (nw, nh))
out = np.full((new_size, new_size, 3), 114)     # 灰边
out[top:top+nh, left:left+nw] = img
```

**为什么不能直接 resize**：直接拉伸会让手变胖/变瘦，模型见过的是保持长宽比的图，
拉伸后精度会掉。而且 YOLO 训练时就是 letterbox，推理必须一致。

#### 4.2 预处理

```python
blob = cv2.cvtColor(img, cv2.COLOR_BGR2RGB)   # BGR → RGB
blob = blob.astype(np.float32) / 255.0        # 归一化
blob = np.transpose(blob, (2, 0, 1))[None]    # HWC → 1CHW
```

**三个顺序都不能错**：颜色通道、数值范围、维度顺序。
任何一处错，模型都能输出东西（不报错），但结果全是垃圾 —— 这种 bug 最难查。

#### 4.3 输出解码（兼容 v5 / v8 两种格式）

```python
# YOLOv8/11: 输出 (1, 4+nc, 8400)  → 需要转置
# YOLOv5:    输出 (1, 25200, 5+nc) → 不需要
if out.shape[0] < out.shape[1] and out.shape[0] <= 4 + nc + 1:
    out = out.T          # v8
    self.fmt = "v8"
else:
    self.fmt = "v5"
```

- v8 没有 objectness，置信度 = 类别分数
- v5 有 objectness，置信度 = obj × cls

**为什么写成自适应**：以后换模型（v5/v8/v11）不用改代码。

#### 4.4 NMS + 坐标还原

```python
# cxcywh → xyxy，然后按 letterbox 参数还原到原图
boxes[:, [0, 2]] = (boxes[:, [0, 2]] - left) / r
boxes[:, [1, 3]] = (boxes[:, [1, 3]] - top) / r
boxes = np.clip(boxes, 0, [W-1, H-1, W-1, H-1])
```

**新手最容易忘的就是这一步还原**。忘了的话框会偏到左上角。

NMS 用纯 numpy 手写（20 行），不依赖 cv2 或 torch：

```python
order = scores.argsort()[::-1]
while order.size > 0:
    i = order[0]; keep.append(i)
    iou = 交并比(box[i], box[order[1:]])
    order = order[1:][iou <= iou_thres]
```

### 阶段 5：写输出层

**核心文件：`led_out.py`**

```python
def _write(self, pin, val):
    if self._cache.get(pin) == val:
        return                      # ★ 避免无意义写 sysfs
    with open(f"/sys/class/leds/{pin}/brightness", "w") as f:
        f.write("1" if val else "0")
    self._cache[pin] = val
```

**两个细节**：

1. **缓存**：每帧都写 sysfs 会产生大量内核调用，加缓存后只在变化时写。
2. **规则封装**：`set_gesture(name)` 内部保证"只有一个为 1，其余为 0"，
   调用方不用关心其他引脚。

**权限问题**：`/sys/class/leds/*/brightness` 默认 `root:root 644`，
普通用户写不了；但 `pip --user` 装的包 root 又看不到（`sudo` 后 `ModuleNotFoundError`）。

解决：装 udev 规则

```bash
# /etc/udev/rules.d/99-kickpi-led-acc.rules
SUBSYSTEM=="leds", KERNEL=="gpio*", RUN+="/bin/chmod 666 /sys/class/leds/%k/brightness"
```

**知识点**：udev 规则在设备出现时执行，所以权限能扛住重启。
比在 `/etc/rc.local` 里 chmod 更规范。

### 阶段 6：集成与调参

**核心文件：`main.py`**

```
while True:
    frame = read()                      # 取帧
    dets  = detector.detect(frame)      # 推理
    label = 最高分那个框的类别
    ── 时间平滑 ──
    if label == 上一帧: same_count += 1
    if same_count >= 5 and label != 当前手势:
        当前手势 = label
        led.set_gesture(label)
    if label is None and empty_count >= 10:
        led.all_off()
```

**为什么必须做时间平滑**

单帧检测会抖：手在动、光照变化、置信度在阈值附近浮动。
不做平滑的话，引脚会以每帧几赫兹的频率乱跳，看着像故障。

两个参数：
- `stable_frames: 5` —— 连续 5 帧同手势才切换（防误检）
- `no_gesture_frames: 10` —— 连续 10 帧没检测到才关灯（防闪烁）

**取舍**：数值越大越稳，但响应越慢。4 fps 下 5 帧 = 1.25 秒，
手感刚好；10 帧关灯 = 2.5 秒，略显迟钝但可接受。

### 问题 11 的完整诊断路径（最值得学）

这是唯一一个"软件完全正常但硬件不行"的问题，诊断思路值得记住：

```
现象：三颗 LED 亮度不同
  ↓
第一步：排除软件 —— 查 pinctrl
  pinconf-pins 显示三个脚驱动能力都是 12mA，MUX 都是 GPIO
  → 软件配置一致，问题在硬件
  ↓
第二步：找硬件差异 —— 查原理图
  pdftotext -layout 原理图.pdf sch.txt
  grep -n "VCCIO.*Domain" sch.txt        → 找到 7 个电压域
  找 GPIO1_D0 在哪一行，往上找最近的域  → VCCIO2
  找 GPIO3_B6                            → VCCIO5
  ↓
第三步：确认电压
  VCCIO2 段写着 "Operating Voltage=1.8V/3.3V"，供电 VCCIO_FLASH
  VCCIO5 段写着 供电 VCC_3V3
  → 1.8V vs 3.3V
  ↓
第四步：用物理常识解释现象
  LED Vf≈2.0V：(3.3-2.0)/220Ω ≈ 6mA（亮）
              (1.8-2.0) < 0    → 不导通（暗/灭）
  → 完全吻合
  ↓
第五步：验证（万用表实测 1.8V / 3.3V）
  ↓
解决：换到 3.3V 域的引脚
```

**方法论**：**软件配置一致时，立刻转向查硬件资料，不要在软件里继续猜。**

## 五、五条可复用的方法论

### 1. 先勘察，再动手

拿到任何新板子/新需求，第一步永远是"列出我有什么"，而不是"写代码"。
一条 `probe_*.sh` 脚本能省几小时。

### 2. 端点先验证

写主程序前，把**输入**和**输出**各自用最小脚本验证一遍，并保存证据（截图/日志）。
出问题时可以二分：是输入、算法、还是输出。

### 3. 分层验证

模型单独用静态图验证，不要一上来就接摄像头。
每一层都独立可信之后，集成才有意义。

### 4. 报错信息要"读到底"

- `pip: Could not find a version` → 可能是 pip 太老，不是包不存在
- `add-apt-repository` 成功 → 不代表有你要的架构的包
- `export 成功` → 不代表引脚真的能驱动

**每一条"成功"和"失败"都要问一句：这个信号真的证明我想的那件事吗？**

### 5. 软件排除后立刻转硬件

三个脚软件配置一样但表现不同 → 不要再写脚本调参数，去查原理图和万用表。

## 八、最后：这个项目真正教给你的

项目的价值不在"跑通了一个手势识别"，而在于：

1. **一个完整的边缘 AI 链路长什么样** —— 采集 → 预处理 → 推理 → 后处理 → 执行
2. **板端部署和 PC 端开发的差别** —— 没有 GPU、pip 是旧的、网络受限、权限要处理
3. **软硬件交界的排错思路** —— 什么时候该怀疑代码，什么时候该怀疑电压
4. **"资源受限时怎么绕"** —— 没有 ONNX 就自己导，没有 PPU 就用 CPU，没有 3.3V 就换引脚

这些经验换个板子、换个模型、换个任务，依然适用。
